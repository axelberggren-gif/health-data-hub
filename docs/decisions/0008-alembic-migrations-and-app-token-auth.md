# 0008 — Alembic migrations and a single app token for the data routes

- **Status:** Accepted
- **Date:** 2026-08-04

## Context

The V1 super-app build (`docs/specs/TECH_SPEC_V1.md`) adds roughly ten new tables over the
coming milestones — daily summaries, baselines, check-ins, weather, insight cards, and the
reserved tables for labs and food. Two things were missing before any of that could land
safely.

**1. There was no migration tool.** `app/db.py` said "production uses Alembic", but Alembic
was neither installed nor configured; the only way the schema was ever created was
`create_all()` on startup, which can add a *new* table but can never change an *existing*
one. With six months of real WHOOP and Mill data in the local database, the first schema
change would have meant hand-editing SQL or dropping the data — for a non-technical owner,
neither is acceptable.

**2. Nothing guarded the data routes.** `/export` returns the entire canonical store —
sleep, recovery, workouts — over plain HTTP with no authentication. That is survivable
while the app only ever listens on localhost, but the V1 dashboard is meant to be opened
from a phone, and the moment it is reachable on the home network, or later on a hosted box,
every one of those routes is public. Auth that arrives after the routes do is a migration
of every caller; auth that ships with the first route is free.

## Decision

**Alembic is the only path for schema change.** `alembic.ini` + `alembic/env.py` are
configured so migrations always target the same database as the app (the URL comes from
`Settings`, never from a tracked file), and revision `0001` is a baseline autogenerated from
`Base.metadata` — an empty database upgraded to head matches exactly what `create_all()`
would have produced. `tests/test_migrations.py` asserts that equality, and CI additionally
replays `alembic upgrade head` from the command line on a scratch SQLite file, so a model
change that forgets its migration turns the `build` check red.

`init_db()`/`create_all()` stays for the dev convenience of brand-new tables, but the rule
is: **never change an existing table without a revision.**

**One shared bearer token guards the data routes.** `Settings.app_token` — empty by default,
which disables the check — is enforced by a single dependency (`app/api/deps.py::require_token`)
mounted on whole routers. It accepts `Authorization: Bearer <token>` or an `app_token`
cookie (the form the PWA will use), and compares with `secrets.compare_digest`. `/export`
is behind it now; `/dashboard`, `/log` and `/insights` mount the same dependency as they
land. `/health` and `/` stay public so uptime checks keep working.

## Consequences

- Schema changes are reviewable diffs with an `upgrade()` *and* a `downgrade()`, and the
  owner's real database can be upgraded in place with `make migrate` instead of being
  rebuilt.
- Every new table from here on costs one extra step (`make migration m="…"`) and CI will
  say so if it is skipped.
- The auth model is deliberately crude: one token, one user, no expiry, no rotation
  workflow. It is the right size for a laptop-hosted single-user app and it is explicitly
  *not* enough for a hosted deployment — that upgrade (real sessions, per-device tokens)
  happens in one place when hosting moves off localhost (tech spec D6, revisit in V2).
- A token in the URL (`?token=…`) is how the PWA will bootstrap its cookie; that lands with
  the PWA in M6, and query-string tokens can leak into server logs — worth remembering when
  this app stops being localhost-only.
